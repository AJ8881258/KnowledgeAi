## 任务 1：用户资料/邮箱设置

目标：支撑 `/Settings` 中的邮箱或账号资料设置。

建议接口：

```http
GET /api/auth/me
PATCH /api/auth/me
```

注意：

- `GET /api/auth/me` 已存在，但当前只返回 `id`、`username`、`role`。
- 如果要保存邮箱，需要确认 `users` 表是否新增 `email` 字段；如果新增，必须用新的 Flyway 迁移。
- 本阶段邮箱默认只是资料字段，不做邮箱验证码和邮件发送。

## 任务 2：模型配置

目标：明确 `/Settings` 中模型配置是否可由用户保存，还是只展示后端环境变量配置状态。

建议优先方案：

- 学习版先不做用户级模型密钥保存。
- 后端提供只读状态接口，例如返回模型是否已配置、模型名、base URL 是否存在，但绝不返回 API key 明文。
- 如果用户明确要做用户级模型配置，再新增表和接口。

候选接口：

```http
GET /api/settings/model
PATCH /api/settings/model
```

## 任务 3：RAG 参数

目标：让 `/Settings` 中的 RAG 参数不是假保存。

需要先确认：

- 参数作用域是用户级，还是知识库级。
- 参数包括哪些：检索 topK、回答温度、最大上下文片段数、是否显示引用等。
- 后端 Chat/RAG 流程是否真正读取这些参数。

候选接口：

```http
GET /api/settings/rag
PATCH /api/settings/rag
```

## 任务 4：删除账号/删除当前用户数据

目标：支撑 `/Settings` 中危险区删除功能。

建议接口：

```http
DELETE /api/auth/me
```

要求：

- 必须基于当前 JWT 用户删除，不能传 userId 删除别人。
- 删除范围必须明确：用户、知识库、文档、chunks、会话、消息、引用来源。
- 必须在事务内完成。
- 数据库外键级联需要确认，不足的地方由 service 显式删除。
- 前端必须二次确认；后端仍然必须做权限边界。

## 注释要求

只在关键逻辑上加注释：

- 新增或修改的功能点要在代码旁补简短说明，尤其是新增字段、DTO、接口方法、Service 分支、事务删除、配置读取、RAG 参数应用等地方，说明这段代码实现什么业务、和旧逻辑有什么区别，方便用户不用逐行对比 diff。
- 权限校验：知识库、文档、会话必须属于当前 JWT 用户。
- 用户资料：只能读取和修改当前 JWT 用户自己的资料。
- 状态流转：文档上传、解析、切片、失败状态要清楚。
- 事务边界：删除知识库、文档、会话、账号时保持数据一致。
- 检索边界：搜索只能查当前用户自己的 `INDEXED` 文档 chunks。
- 模型配置：不泄露 API key，不把供应商原始敏感错误直接返回前端。
