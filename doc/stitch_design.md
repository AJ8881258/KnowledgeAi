# KnowFlow AI 从 0 开始页面设计提示词

请从 0 开始为一个名为 **KnowFlow AI** 的 Web 应用设计完整产品界面。你不能假设自己能看到源码、截图或当前页面，所以请完全根据下面的产品说明、功能范围、页面结构和设计约束来生成设计方案。目标不是做营销官网，而是做一个真实可用、专业、清爽、有设计感的 **智能知识库 + RAG 问答 SaaS 工作台**。

请输出一套完整的应用界面设计，覆盖桌面端和移动端响应式状态。设计应能指导前端用 React + Tailwind CSS + shadcn/radix 风格组件实现。

## 1. 产品定位

KnowFlow AI 是一个智能知识库问答平台。用户可以上传学习资料、项目文档、产品文档或内部知识材料，系统会解析文档、切片、索引，并允许用户基于自己的知识库进行 AI 问答。回答需要展示引用来源，方便用户确认答案来自哪些文档片段。

产品核心价值：

- 把零散文档整理成可检索、可问答的知识库。
- 让用户用自然语言询问自己的资料，而不是手动翻文档。
- 回答必须有引用来源，强调可信、可追溯、可复核。
- 面向学习、项目管理、产品文档、知识沉淀和轻量团队协作场景。

目标用户：

- 学生或学习者：上传课程资料、笔记、PDF、Markdown，进行复习问答。
- 开发者或项目成员：上传项目文档、接口说明、需求文档，快速定位信息。
- 产品/运营人员：管理产品资料、FAQ、版本说明，进行知识问答。
- 小团队：共享知识库，控制成员权限，沉淀团队知识。

整体气质：

- 专业智能 SaaS。
- 清爽、可信、现代，但不要花哨。
- 更像“知识工作台 / 文档管理器 / AI 助理”，不是宣传页。
- 信息密度要适合长期使用，不能只有大卡片和空洞装饰。

## 2. 当前已具备的 MVP 功能

请把以下功能作为当前产品已经可用的核心能力来设计：

### 认证

- 用户注册。
- 用户登录。
- JWT 登录态。
- 重置密码。
- 当前用户信息读取。
- 未登录用户访问主应用时跳转登录页。
- 登录后进入主应用工作台。

### Dashboard 首页

- 展示当前账号的数据概览。
- 统计知识库数量、文档数量、可检索片段数量、会话数量等。
- 展示最近知识库、最近文档、最近会话。
- 展示核心流程入口：创建知识库、上传文档、开始问答。
- 数据来自真实接口，不是静态 mock。

### Knowledge Bases 知识库

- 查看知识库列表。
- 创建知识库。
- 编辑知识库名称、描述、主题色或精选状态。
- 删除知识库。
- 查看知识库详情。
- 每个知识库有状态、创建时间、更新时间、文档数量、chunk 数量、可检索来源等信息。
- 知识库按当前用户隔离，用户只能看到自己的知识库。
- 知识库详情页保留“文档检索测试区”，用于检索文档片段。
- 知识库详情页当前不承载 RAG 对话入口，正式问答入口在 Chat 页面。

### Documents 文档

- 按知识库上传文档。
- 支持第一版格式：TXT、Markdown、文本型 PDF。
- 文档上传后经历状态流转：
  - UPLOADED
  - PROCESSING
  - INDEXED
  - FAILED
- 系统会解析文档文本、切片并建立可检索内容。
- 查看文档列表。
- 查看文档详情。
- 查看文档 chunks 或索引片段信息。
- 删除文档。
- 删除文档时级联删除 chunks。
- 文档属于当前用户自己的知识库，不能跨用户访问。

### Search 文档检索

- 在某个知识库内输入关键词检索文档 chunks。
- 当前 MVP 是 PostgreSQL 普通关键词匹配。
- 检索结果展示：
  - 文档名
  - chunk 序号
  - 内容片段
  - 分数 score
- 搜索结果只来自当前用户自己的知识库和已完成索引的文档。
- 没有结果、加载失败、未索引文档等状态需要清晰展示。

### Chat / RAG 问答

- 选择知识库后创建问答会话。
- 查看会话列表。
- 会话支持重命名。
- 会话支持删除。
- 会话支持置顶和取消置顶。
- 查看会话消息。
- 发送问题，系统先检索知识库 chunks，再构造 prompt 调用模型，最后返回回答。
- AI 回答展示引用来源。
- 引用来源来自检索结果，包含文档名、chunk、分数和片段。
- 当前 MVP 是非流式回答。
- 模型调用失败时显示清晰错误，不泄露 API key、base URL 或供应商敏感错误。
- `/Chat/{sessionId}` 切换会话时，体验上应只刷新消息区域，不要让整个应用明显闪烁。

### Settings 设置

当前 Settings 需要设计成“真实状态清楚”的页面，不能出现假功能：

- 账号资料：用户名、角色、可能的邮箱字段。
- 邮箱功能当前可能只是资料字段，未必有邮箱验证流程。
- 模型配置：可能由后端环境变量管理，也可能未来支持用户级配置。
- API key 绝不能明文展示。
- RAG 参数：需要明确是用户级、知识库级还是仅本地偏好。
- 如果后端没有实际使用某些参数，不能显示成“已生效”。
- 删除账号 / 删除当前用户数据：必须有危险区、二次确认、删除范围说明。
- 如果某项能力尚未实现，应以“只读说明 / 禁用状态 / 即将支持”呈现，不要设计可点击的假保存按钮。
- 退出登录。

## 3. 未来规划功能

请在整体产品信息架构和页面设计中预留以下未来功能。它们可以出现在导航、页面区块、空状态、禁用态、路线图提示、Coming soon badge 或高级设置中，但必须清楚区分“当前可用”和“未来规划”。

### 阶段 8：Settings 功能接入与交付整理

- 邮箱 / 账号资料编辑。
- 模型配置状态读取。
- 用户级或管理员级模型配置保存。
- API key 脱敏展示。
- RAG 参数读取与保存。
- 删除账号及当前用户全部数据。
- 删除范围包括：用户、知识库、文档、chunks、会话、消息、引用来源。
- 项目交付信息：演示账号、启动说明、架构说明、RAG 流程说明。

### 阶段 9：检索质量升级

- 从普通关键词检索升级到更可靠的检索。
- 可能路线：
  - PostgreSQL 全文检索。
  - embedding + pgvector 向量检索。
  - 混合检索。
- 检索结果需要更有区分度的 score。
- 支持在检索测试区对比关键词检索和新检索效果。
- 支持展示命中原因、关键词高亮、向量相似度或检索策略。
- 未来可加入重建索引、索引健康状态、检索质量评估。

### 阶段 10：RAG 体验增强

- 流式输出，用户能看到回答逐步生成。
- 多轮上下文增强。
- 引用定位增强，可以更清楚看到回答的哪部分来自哪个文档片段。
- 空检索结果时提供降级提示。
- 模型失败、超时、限流时有明确状态。
- 支持停止生成、重新生成、复制回答、查看引用详情。
- 未来可能支持多模型选择，但不能泄露模型密钥。

### 阶段 11：文档处理增强

- OCR，支持扫描型 PDF 和图片文字识别。
- 更多文件格式，例如 DOCX、PPTX、XLSX、HTML。
- 后台处理队列。
- 失败重试。
- 批量上传。
- 文档处理进度条。
- 文档解析日志或失败原因。
- 文档重新解析、重新切片、重新索引。
- 文件大小、格式、解析质量提示。

### 阶段 12：权限与团队协作

- 从个人知识库扩展到团队空间。
- 支持共享知识库。
- 成员角色：
  - owner
  - editor
  - viewer
- 知识库级权限控制。
- 团队成员管理。
- 邀请成员。
- 操作审计。
- 保留个人空间，不破坏当前个人用户隔离。
- 共享资源查询必须有权限边界。

### 阶段 13：部署与运维

- 生产环境配置状态。
- 日志监控。
- 备份与恢复。
- 部署脚本或部署状态。
- 健康检查。
- 存储、数据库、模型服务连接状态。
- 管理员运维视图可以作为未来高级功能，不要影响普通用户主流程。

## 4. 必须设计的页面

请至少设计以下页面或视图。每个页面都要考虑加载态、空状态、错误态、禁用态、移动端状态。

### 4.3 Dashboard

- 筛选或排序。
- 卡片视图 / 列表视图切换。

### 4.6 Chat / RAG

用途：正式知识库问答入口。

必须包含：

- 知识库选择区。
- 会话列表。
- 会话操作：新建、重命名、删除、置顶/取消置顶。
- 消息区。
- 用户消息。
- AI 回答。
- 引用来源。
- 输入框。
- 发送按钮。

推荐桌面结构：

- 左栏：知识库选择 + 当前知识库状态。
- 中栏：会话列表。

- 默认显示消息区。

- 未来功能如果未实现，使用 disabled、Coming soon 或 Roadmap 标签。

## 5. 视觉设计要求

### 风格

采用“专业智能 SaaS 工作台”风格：

- 浅色为主。
- 清爽、现代、克制。
- 适合长时间阅读文档和问答。
- 有 AI 产品感，但不是科幻大屏。
- 有层次，但不堆装饰。

### 色彩

建议：

- 主色：蓝色或青蓝色，用于主要按钮、激活导航、重点状态。
- 辅助色：绿色表示成功/已索引，琥珀表示处理中/警告，红色表示失败/危险操作。
- 背景：off-white、slate、neutral 分层。
- 文字：高对比深色，次级文字使用 slate/neutral。
- 不要全站只用一种蓝色。
- 不要大面积紫蓝渐变。
- 不要装饰光球、bokeh、随机渐变块。

### 字体与排版

- 中文界面为主，英文用于导航标签和技术状态。
- 正文至少 14-16px。
- 工作台标题不要过大。
- 表格、卡片、badge 内文字不能溢出。
- 数字统计可使用 tabular numbers。
- 行高舒适，适合文档阅读。

### 圆角、边框、阴影

- 卡片和面板圆角 6-8px。
- 按钮和输入框圆角统一。
- 使用细边框和轻阴影建立层级。
- 不要过度圆润。
- 不要卡片套卡片。
- 不要夸张投影或发光。

### 图标

- 使用 Lucide 风格线性图标。
- 图标线宽统一。
- 不使用 emoji 作为功能图标。
- 图标按钮必须有 tooltip 或 aria-label。

### 动效

- 动效用于状态转换、抽屉展开、hover/pressed、列表进入、消息生成。
- 时长 150-250ms。
- 使用 transform/opacity，不要动画 width/height 导致布局跳动。
- 支持 reduced-motion。
- 不要用纯装饰动画干扰工作台。

## 6. 组件规范

请设计统一组件体系：

- Button：primary、secondary、outline、ghost、destructive、disabled、loading。
- Input / Textarea：label、helper、error、disabled、readonly。
- Select / Combobox：用于知识库选择、模型选择、筛选。
- Tabs / Segmented Control：用于列表视图切换、检索策略切换。
- Badge：状态、权限、规划、索引状态。
- Table：文档列表、检索结果、成员列表。
- Card：统计摘要、知识库卡片、最近记录。
- Dialog / Alert Dialog：删除确认、重命名、危险操作确认。
- Sheet / Drawer：移动端侧栏、文档详情、引用详情。
- Toast：保存成功、失败、上传状态。
- Skeleton：加载中。
- Empty State：无知识库、无文档、无会话、无检索结果。
- Error State：接口失败、模型失败、权限失败、文档处理失败。

## 8. 状态设计要求

每个核心页面都要考虑：

- 初始加载。
- 局部加载。
- 空状态。
- 错误状态。
- 权限失效。
- 提交中。
- 保存成功。
- 保存失败。
- 删除确认。
- 禁用状态。
- 未来功能状态。
- 后端未接入状态。

重要原则：

- 当前可用功能和未来规划功能必须视觉区分。
- 未实现功能不能设计成可点击后显示成功。
- 对用户有风险的操作必须有二次确认。
- 模型密钥、base URL、供应商敏感错误不能泄露。
